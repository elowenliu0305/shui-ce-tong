# Phase 0 Research: 税策通第一版

以下决策已经由产品负责人确认，不再作为实施阶段的开放问题。

## 1. 前端架构

**Decision**: 现有 HTML/CSS/JavaScript 是视觉、题目和交互原型；正式前端使用 React、TypeScript 和 Vite 重构。

**Rationale**: 第一版包含 39 个页面/页面状态、多企业上下文、不可变报告和后续 Supabase 替换，单文件原生 JS 会继续放大状态与视图耦合。

## 2. 前后端推进顺序

**Decision**: 先用 typed service interfaces + Mock Service 完成并验收前端；随后再设计 Supabase、资料导入、规则后端和 AI Agent。

**Rationale**: 产品负责人要求先确认全链路、再推进前端、最后设计后端。服务契约让前端成果可被真实服务替换，而不是后端接入时重写页面。

## 3. 身份与企业

**Decision**: 第一版使用邮箱和密码；正式注册验证邮箱并支持邮件重置密码。一个账号管理多家企业，不做多人协作。企业可以永久删除，并级联删除其业务资产；账号收藏保留。

**Rationale**: 避免短信供应商与国内送达率成为第一版阻塞项，同时保持数据归属简单。

## 4. 企业经营信息与风险问卷

**Decision**: 企业经营信息与现有 HTML 的 10 道题是两组独立输入。经营信息用于政策筛选和节税估算；10 道题用于风险与健康度。

**Rationale**: PRD 的经营字段不能替代用户明确指定的 10 道题；混为一组会使风险和政策条件无法解释。

## 5. 风险与健康度

**Decision**: 10 题同权。每题安全答案=0，异常答案=1，不清楚=0 但生成待核验。0–2/3–5/6–10 分别为低/中/高风险；健康度为 `(10-riskCount)×10%`。

**Rationale**: 规则简单、透明、可直接验收，并替代原 Demo 固定 86% 的误导行为。

## 6. 政策规则与节税

**Decision**: 规则内部使用 pass/fail/unknown；面向报告只展示 eligible 与 pending，ineligible 隐藏。金额只有在资格、必需输入和公式完整时计算，互斥/重叠政策不重复累加。

**Rationale**: 大模型或模糊百分比无法替代确定性政策条件；金额必须可复现和审计。

## 7. 报告快照

**Decision**: 每次完成体检创建不可变 AssessmentRun 和 ReportSnapshot，保存输入、规则/政策版本和结果。重新测评只追加。

**Rationale**: 历史报告必须能复现当时结论，不能随当前企业信息或政策更新漂移。

## 8. 完整资料库

**Decision**: 资料包全部源文件进入清单和搜索库。重复来源保留并归入规范资料关系；所有资料可查看正文和下载原文件。只有结构化并核验的有效政策参与匹配、风险依据和金额计算。

**Rationale**: “能否出现在资料库”和“能否驱动权威计算”是两个不同权限；不能因暂不匹配而丢弃用户要求展示的资料。

## 9. 搜索与 RAG

**Decision**: 首页/资料库搜索覆盖标题、文号、机构、元数据和全文。后端使用关键词与向量混合检索，资料切分保留标题、文号、机构、章节与原文定位。

**Rationale**: 文号需要精确检索，口语问题需要语义检索；单一向量或单一关键词都不够稳定。

## 10. Embedding 模型

**Decision**: 第一版使用 `Qwen/Qwen3-Embedding-0.6B`，1024 维归一化向量和 Cosine 相似度。条款/段落目标 600–900 个中文字符，最大 1200，重叠约 120。精度不足时增加 `Qwen3-Reranker-0.6B`。

**Rationale**: 该模型兼顾中文检索、长文本、可本地部署和成本。模型版本必须记录；更换模型需全量重建向量。

## 11. AI Agent 定位

**Decision**: Agent 可以回答非税收普通问题，并自然引导小微企业融资、现金流、成本、预算、经营、税费与政策支持。税务/政策/案例问题强制 RAG+引用；企业/报告问题调用脱敏上下文和规则结果。

**Rationale**: 产品需要持续服务能力而不是封闭的税务 FAQ，同时必须避免把无依据的模型回答包装成税务结论。

## 12. Agent 工具边界

**Decision**: 后端预留当前企业、报告快照、知识检索、收藏/历史、规则解释和私有文件检索六类工具。普通问题可不调用 RAG；税务问题检索不到依据时返回 insufficient-evidence。

**Rationale**: 明确工具路由才能测试普通问题、税务问题和企业上下文问题的不同表现。

## 13. 隐私与密钥

**Decision**: 不向模型发送邮箱、企业名称、统一社会信用代码或无关完整文件。模型与 Embedding API Key 只存在服务端环境变量，不进入浏览器或 Git。真实文件只有用户明确发起任务后才能检索。

**Rationale**: 静态前端无法保护密钥；企业税务与经营数据必须最小化暴露。

## 14. 测试策略

**Decision**: Vitest 验证领域规则，React Testing Library 验证组件与页面状态，Playwright 验证移动端主链路、路由、企业隔离和历史快照。

**Rationale**: 税务规则需要组合边界测试，页面需要错误/空状态，完整链路还需真实浏览器与视口验收。

## Deferred Until Backend Design

以下内容不阻塞 React 前端，但必须在前端 contracts 冻结后设计：

- Supabase 具体表、索引、外键、级联和 RLS。
- Edge Functions 与独立服务的职责边界。
- 生产环境问答模型 API 和供应商。
- Word 解析器、中文全文索引实现与 reranker 启用阈值。
- 资料审核操作是脚本、内部工具还是后续管理后台。
