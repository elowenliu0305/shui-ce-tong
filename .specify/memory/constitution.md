# 税策通 Constitution

## Core Principles

### I. 证据先于结论（NON-NEGOTIABLE）

每条政策、案例、风险或测算结论必须能追溯到结构化来源、规则版本和当次输入。原文事实、产品规则与推断必须分层展示；无法核验时必须明确显示“待确认/待补数据”，不得编造异常笔数、适用资格或节税金额。

### II. 结果必须由输入驱动

企业画像、风险问卷、材料状态和政策条件是唯一允许驱动体检结果的输入。同一输入应产生可复现结果，不同关键输入应产生可解释差异。任何健康度、匹配等级、风险等级和金额区间都必须有透明的计算口径。

### III. 数据最小化与企业隔离

系统只处理完成当前功能所需的最小数据，不持久化密码、验证码或未经授权的文件内容。企业画像、报告、会话和文件记录必须以企业 ID 隔离；政策与案例收藏按账号保存。发送给模型的企业上下文必须脱敏且最小化，真实文件只有在用户明确发起任务后才能进入检索或分析链路。

### IV. 移动优先、可访问、可验收

核心链路必须在 360–430px 视口可用且无横向溢出；主要触控目标原则上不小于 44px，并具备键盘焦点和非颜色提示。每个用户故事必须具备可独立执行的验收场景，控制台不得出现未捕获错误。

### V. 契约优先与渐进交付

先锁定用户链路、页面状态和领域契约，再推进前端与后端。现有 HTML 作为视觉和交互原型；正式前端使用已批准的 React、TypeScript 与 Vite，并通过 Mock Service 验收完整链路。前端通过稳定服务契约与后端解耦，随后再设计 Supabase、规则引擎、资料导入与 AI Agent；每个阶段都必须保持主链路可运行。

## Product and Domain Constraints

- 产品定位为面向小微企业的税务与经营辅助工具。AI Agent 可以回答普通问题并引导企业金融与经营场景，但不替代税务机关口径、专业税务/法律/投资意见，也不执行真实申报。
- 资料包全部资料进入可搜索资料库；只有完成结构化条件与来源核验的政策可以参与企业匹配、风险依据和金额计算。
- 金额测算必须同时具备所需输入、可展示公式和适用规则；否则只展示待补项。
- 历史报告是不可变时间快照，查看旧报告不得被当前画像或规则覆盖。
- 当前实施阶段先完成 React 前端和 Mock 契约；Supabase 鉴权、数据库、RLS、真实资料解析、RAG 和 Agent 工具调用在前端验收后进入后端阶段。多人权限与管理员后台不在第一版范围。

## Development Workflow and Quality Gates

1. 需求先进入 feature spec，再生成计划、数据模型、契约和任务。
2. 结构化知识、规则和持久化状态必须有明确 schema、版本号与迁移策略。
3. 合并前至少通过语法检查、确定性规则测试、关键链路浏览器验收、360/390px 响应式检查和来源抽样核对。
4. Review 必须检查：输入是否真正驱动结果、结论是否可追溯、是否保存敏感数据、历史快照是否不可变。
5. 违反本章原则的设计必须在 `plan.md` 的 Complexity Tracking 中说明理由、影响和被否决的简单替代方案；无法合理说明则不得进入实现。

## Governance

本 Constitution 优先于临时实现偏好。原则变更必须同步更新版本、修订日期和受影响的 spec/plan，并说明迁移方案。重大或破坏性变更提升主版本，新增强制原则提升次版本，文字澄清提升修订版本。
